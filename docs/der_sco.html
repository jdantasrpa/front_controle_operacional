Decisões de modelagem

Chave técnica + chave natural

Toda tabela recebe id bigint identity como PK. As chaves imutáveis do domínio (CNPJ, nome, numero_convenio) viram UNIQUE — FKs referenciam o id, não o texto, para permitir correção sem quebrar vínculos.

O vínculo é o centro

vinculo (convênio × originadora) é o hub. Conciliação, custo, responsável, remessa, financeiro e abas do analítico penduram nele — não no convênio mestre.

Competência como texto AAAA-MM

char(7) (ex.: 2026-07) espelha o file-store e ordena lexicograficamente. Alternativa: date truncado ao 1º dia — decidir na revisão.

Custo versionado, não sobrescrito

custo guarda histórico por vigência + status ATIVO/INATIVO. custo_faixa só existe no método FAIXA. O custo vigente é calculado por competência.

Financeiro registra o custo aplicado

repasse.custo_id + custo_aplicado + devendo gravam o snapshot auditável: qual regra de custo entrou no cálculo e o resultado. status_financeiro é definido pelo backend.

Status independentes

Gestão (convenio.status) e Conciliação (gerencia_conciliacao.em_conciliacao_ativa) não se influenciam — só se exibem lado a lado. Modelados em tabelas distintas.

Auditoria em toda tabela mutável

Colunas criado_em / atualizado_em (timestamptz) e ator. Histórico de responsável em tabela dedicada (responsavel_historico).

Indicadores = VIEW

Os indicadores de conciliação (mês/quadrimestre/ano) não são tabela: VIEW (ou materialized view) agregando vencimentario. Zero duplicação de dado.

Pontos a decidir

  • Competência: manter char(7) AAAA-MM ou migrar para date (1º dia do mês)?
  • Remessa: remessa_envio 1:1 com o vencimentário (como está) ou permitir múltiplos envios por vencimento (histórico de reenvio)?
  • Modelo de envio (particularidade) é múltiplo → normalizar em tabela particularidade_envio (N:N) ou manter como array/texto?
  • Grupo master: a originadora já agrupa convênios via vinculo. A tabela grupo/convenio_grupo é para uma 2ª dimensão de agrupamento — confirmar se é necessária.
  • Usuários: aproveitar auth.users nativo do Supabase e ligar usuario por uuid, ou manter tabela própria com senha_hash?
  • Enums: transformar status/método/situação em ENUM nativos do Postgres (mais rígido) ou manter text + CHECK constraint?
